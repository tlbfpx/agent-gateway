## 1. 决策矩阵（Explore 报告量化 + 子代理提案交叉验证）

公式：`综合优先级 = 业务价值 × 0.4 + 技术依赖 × 0.3 + (5 - 现有覆盖) × 0.3`
评分依据：Explore 子代理（`6bfff8e9`）全仓扫描 + 4 个 backend-architect 提案的难度/依赖声明。

**打分细则**（评审建议 #5 采纳）：
- **业务价值**（1-5）：该主题上线后能解锁的功能数 × 0.5 + 紧迫性（用户是否天天问）× 0.5
- **技术依赖**（1-5）：前置依赖数量反向得分（5=无前置，1=多个跨模块耦合）
- **现有覆盖**（1-5）：已有可用代码行 / 估计总代码行（5=完全落地，1=空白）

| 主题 | 业务价值 | 技术依赖 | 现有覆盖(原始) | 现有覆盖得分 | 验算 | 综合 | **推荐** |
|---|---:|---:|---:|---:|---|---:|:---:|
| **D1** IAM/RBAC 深化 | 5 | 4 | 3（端口+UI外壳已落地，缺类型化）| 2 | 5×0.4 + 4×0.3 + 2×0.3 = 2.0+1.2+0.6 | **3.8** | 1️⃣ |
| **D2** 多租户配额+成本 | 5 | 4 | 3（CostRepository+UI已成型，缺主调用链接线）| 2 | 同 D1 公式 | **3.8** | 2️⃣ |
| **D3** RAG 知识库 | 4 | 2 | 1（整章空白，需新建 4 个 Maven 模块）| 4 | 4×0.4 + 2×0.3 + 4×0.3 = 1.6+0.6+1.2 | **3.4** | 3️⃣ |
| **D4** IM 通道 + 开放API深化 | 4 | 3 | 4（§23+§25 已落地，仅 IM 一块真缺）| 1 | 4×0.4 + 3×0.3 + 1×0.3 = 1.6+0.9+0.3 | **2.8** | 4️⃣ |

> 注：D3 与 D4 综合分（3.4 vs 2.8）虽不显著拉开，但**业务定位不同**：D3 是 spec 三期能力（D 阶段末尾收尾即可），D4 的 IM 子项是 spec §24 二期但本项目 IM 通道缺口最显性——故推荐顺序仍把 D4 排在 D3 之前（D4 IM 是"立刻能用"的客户面能力，D3 RAG 是"长期演进"的能力）。

### 关键洞察

1. **D1 与 D2 并列最高分（3.8）**，都是"已有骨架，缺关键接线"型变更，落地阻力最小、ROI 最高
2. **D4 实质缺口仅 IM（§24）**，开放 API（§23）+ Webhook（§25）已落地，scope 比名字暗示的小很多
3. **D3 整体最重**——需新建 4 个 Maven 模块 + 全新依赖（向量库、文档解析器），但属于 spec 三期范畴，**可放到 D 阶段最末**
4. **D2 与 D1 互为依赖**：D2 超额策略需要租户隔离边界 → 依赖 D1 完善；D1 角色权限管理需要"按角色查用量" → 反向受益于 D2。建议 **D1 → D2** 顺序。

### 2.1 D1 IAM/RBAC（≈ 2.5 周，**建议立即立项**）

**目标**：把 RBAC 从"决策引擎"推进到"决策治理"。

**核心工作**（来自 D1 提案 `9b1a2d92` + Explore 缺口）：
- `Role / AgentPermission / ModelPermission / SkillPermission / PolicyPreview` record 类型化（spec §19.2）
- `RoleRepository / RoleBindingRepository / RbacChangePublisher` 三个 domain 出站端口
- `AdminPolicyController` 从 `Map<String,Object>` 切到类型化仓储，**接进 AuthorizationService 评估链**（当前注释承认"评估接线前策略在 preview 中不生效"）
- 补 `/v1/admin/roles` + `/v1/admin/users/{id}/roles` REST
- 纵深防御两处校验点（RbacFilter + A2A 调用前）打 OTel span attribute `rbac.check_point`
- UI 补角色管理 + 用户角色绑定页

**决策点已定**（D1 提案 §3）：策略 DB 直存 + 启动加载 + Nacos 广播（A 方案）；PolicyPreview 走纯函数（A 方案）；审计仅 DENIED 写表（B 方案）。

**错误码段**：GW-1003 复用 + GW-1010~1012 新增 + GW-4204 复用（与 D2/D3/D4 零冲突）。

### 2.2 D2 多租户配额 + 成本计费（≈ 4 周）

**目标**：从"按模型 token 单价"升级到"租户级硬配额 + 实时计费 + 超额策略 + 账单导出"。

**核心工作**（来自 D2 提案 `a0ae1a80` + Explore 缺口）：
- `ChatOrchestrator` 主调用链接线：`recordUsage` 接入（当前仅 InMemoryCostRepository 测试自身在调）
- 真实 token 采集：替换 AdminMetricsController 硬编码 `1500 token` 估算（注释承认"审计无 token 字段"）
- 3 维配额：REQUEST / MODEL_TOKEN / MONEY，按租户×模型×维度独立
- 3 档超额策略：ALERT / THROTTLE / SUSPEND（SUSPEND 必须显式管理员动作 + 5min 冷静期）
- QuotaGate 接入 Orchestrator 前置（参考 §21.4 预算与告警 + §8.3 限流交互点）
- 预算异步校验 + Webhook 告警通道
- 账单导出 CSV（一期）→ 对象存储 + PG 存元数据

**决策点已定**（D2 提案 §3）：Redis 原子计数（B 方案）；异步 MQ 落账（B 方案）；CNY 单币种 + 字典预留（A 方案）；独立 QuotaGate（B 方案）；对象存储（B 方案）。

**错误码段**：GW-4301~4306（沿用 spec §21.6 已规划）。

### 2.3 D4 IM 通道（≈ 3 周）

**目标**：把 §24 二期范围从 0% 推进到 MVP（飞书 + 钉钉双适配器端到端）。

**核心工作**（来自 D4 提案 `61382575` + Explore 缺口）：
- §23 深化 — springdoc `/v1/openapi.json` + 文档门户最小集 + OAuth2 Client Credentials（`/oauth/token`、`/oauth/introspect`）
- §24 IM — `ImChannelGateway` 抽象 + 飞书/钉钉 Adapter + 身份映射 + 会话绑定 + 流式适配（企微放二期）
- §25 Webhook 深化 — `WebhookEventBridge` 升级为公共 `WebhookEventPort`，Redis Stream 重试 + 死信表 + HMAC 签名 + 与 D2 计费事件对接

**决策点已定**（D4 提案 §3）：OAuth2 + API Key 并存（B 方案）；springdoc 内置（A 方案）；Webhook 为主 + 企微长连接（B 方案）；统一 ImChannelGateway 抽象（B 方案）；Redis Stream 重试（B 方案）；HMAC-SHA256（A 方案）。

**错误码段**：GW-45xx（开放 API 深化）+ GW-6xxx（IM）+ GW-7xxx（Webhook）。

### 2.4 D3 RAG 知识库（≈ 4 周）

**目标**：RAG 最小闭环（单知识库 + 向量检索 + ChatOrchestrator 注入）。

**核心工作**（来自 D3 提案 `30711f43` + Explore 缺口）：
- **新建 4 个 Maven 模块**：`gateway-rag-domain` / `gateway-rag-application` / `gateway-rag-infra-parser` / `gateway-rag-infra-vector`
- 4 个 Port：`EmbeddingPort / VectorStorePort / DocumentParserPort / RetrieverPort`
- pgvector 实现（零增量运维起步）+ 切片策略（定长 512 token + 10% 重叠滑窗）
- 上传→解析→切片→Embedding→入库 流水线
- `ChatOrchestrator` 前置 RAG 钩子（Agent 声明 `knowledgeBases` 或会话携带 `kbIds`）
- 知识库 CRUD + 上传 + 检索 API
- 复用 §29 工作流 `RAG_RETRIEVAL` 节点（spec §29 line 1795 已有定义）

**决策点已定**（D3 提案 §3）：MVP pgvector，完整版抽象 `VectorStorePort` 留升级路径（A→B）；定长 512 token + 10% 重叠（A 方案）；复用 LLM Provider Embedding（A 方案）；MVP 纯向量，完整版混合检索。

**错误码段**：GW-5001~5008（新段）。

| 依赖方向 | 说明 |

### 4.2 共性风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 主线整合时遗漏错误码冲突 | 低 | 中 | 本文件 §3 已做冲突扫描并通过 |
| 子代理提案与归档评审结论不一致 | 中 | 中 | 阶段二 OpenSpec 立项前派 `spec-document-reviewer` 单轮复核 |
| 多个主题并行导致 review 评审轮次 ≥ 5 触发熔断 | 低 | 中 | 串行开工（D1 → D2 → D4 → D3），每轮评审 ≤ 3 轮收敛 |
| **D2** SUSPEND 5min 冷静期与 ChatOrchestrator 并发重试的竞态 | 中 | 高 | SUSPEND 标志位由 Redis 原子写锁；AuthFilter 单读；冷静期由定时器续期而非单次 SET |
| **D4** Webhook HMAC secret 轮换期与历史签名的兼容 | 中 | 中 | 订阅方保留最近 2 个 secret（old + new），30 天宽限期；HMAC 签名头附加 `X-Gateway-Signature-Version` |
| **D4** OAuth2 token 撤销的广播链路（依赖 Nacos）| 中 | 中 | access token TTL ≤ 1h，撤销走 Nacos `gateway.auth.revoked` 广播 + Redis 黑名单双写 |
| **D3** pgvector 单点 + 何时切换 Milvus/Qdrant | 中 | 中 | 触发条件：`embedding 总数 > 500万` 或 `p99 检索 > 200ms`；届时通过 `VectorStorePort` 抽象无痛切换，零业务改动 |
